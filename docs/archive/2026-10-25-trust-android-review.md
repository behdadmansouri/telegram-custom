# Review: Android patch 0010 (media trust), origin/feat/trust-android

Patch lines (P) = line numbers in `android/patches/0010-Media-trust-media-from-untrusted-chats-waits-for-a-tap.patch`. Upstream lines = DrKLO 0aae9598 with 0001-0010 applied (`TMessagesProj/src/main/java/org/telegram/`). TrustController file line = P - 173.

## High

1. **The one-time backfill is skipped whenever an incoming message reaches storage before the first refresh.** P808 (`noteIncoming`): the first insert runs `CREATE TABLE IF NOT EXISTS tc_activity`. P855-857 (`refresh`): backfill runs only `if (!database.tableExists("tc_activity"))`. `noteIncoming` is the first statement of `putMessagesInternal` (`MessagesStorage.java:11864`), while `refresh` arrives through two hops on the storage queue (`queueRefresh` P833-843 posts a runnable that posts another). Scenario: the user updates the app; the first thing that wakes it is an FCM push or the startup getDifference; `putMessagesInternal` stores an incoming private message, `noteIncoming` creates the table, then `refresh` finds the table and never backfills. Same thing after every re-login (deviation 3's reason for using the table as the flag). Result: every existing contact counts as 0-1 active days, so rule 7 trusts nobody, and media from all your real contacts stays blurred for weeks until N new days accumulate. Fix: keep a separate marker (a `tc_meta` row, or create the table only in `refresh` and have `noteIncoming` return or buffer until `refresh` has run once), and backfill based on the marker.

2. **Backfill blocks the storage queue for a long time on a big account.** P899-941: one `INSERT OR IGNORE` per incoming private message from the last 365 days, with no transaction and no dedupe (the live feed's `logged` set is not used here). Each statement autocommits. The DB is WAL with the default `synchronous` (no PRAGMA in `MessagesStorage.java:327-330`, no compile flag in jni), i.e. one WAL sync per row. Every row is also deserialized with `TLdeserialize`. It runs on the storage queue, triggered by the first `verdict()` from cell binding. Scenario: 50k cached incoming private messages means 50k commits; for that whole time chat history does not load and sends are not stored. It happens again after each re-login. Fix: `database.beginTransaction()`/`commitTransaction()` around the loop, and skip a (uid, day) already inserted (an in-memory set) before calling `step()`.

## Medium

3. **Cached videos autoplay in untrusted chats through the HLS-quality path.** `TrustController.isLocal` (P638-639): any `path` not starting with `http` counts as local and passes. `ChatMessageCell.java:10366`, `:18099`, `:18112` autoplay `ImageLocation.getForVideoPath(messageObject.cachedQuality.uri.getPath())` with the message as parent. Scenario: a video with alternative qualities whose file is already on disk (opened before, or the same document seen in a trusted chat) autoplays in the untrusted chat's cell. The spec says "nothing autoplays, including ... videos already on disk". Fix: in `isLocal`, treat `location.imageType == FileLoader.IMAGE_TYPE_ANIMATION` (what `getForVideoPath` sets, `ImageLocation.java:59`) as non-local unless the message is own or tapped, or drop any media location whose path is not the message's own `attachPath`.

4. **Notifications download voice messages from untrusted chats.** `NotificationsController.java:5541-5546`: when previews are on and a voice message's file is missing, `getFileLoader().loadFile(messageObject.getDocument(), ...)` runs with no gate. Scenario: a stranger sends a voice note; building the notification downloads it with no tap (spec: "No media downloads without a tap: ... voice"). Fix: wrap it in `TrustController.getInstance(currentAccount).allows(messageObject)`.

5. **Forwarded stories in chat load their preview with no gate.** `ChatMessageCell.java:10379` → `StoriesUtilities.setImage(photoImage, storyItem)` (`ui/Stories/StoriesUtilities.java:886`, `:897`, `:920`) passes the `StoryItem` as `parentObject`, so the `instanceof MessageObject` test in gate G (P109) is false. Scenario: a stranger forwards a story into an untrusted chat; its 320 px photo, or the video's thumb, fetches and decodes. A4 only closed the auto-download half. Fix: in G, when `parent instanceof ChatMessageCell` and `parentObject` is a `StoryItem`, use the cell's `getMessageObject()`; or wrap the call in `ChatMessageCell` with `allows(messageObject)` (show the stripped bitmap only).

6. **Cached media in an untrusted chat can never be unlocked in the cell, and the cached-photo pass is dead code.**
   - `isLocal` P647: `location.photoSize != null` is false for every full-size photo location: `ImageLocation.getForPhoto(PhotoSize, Photo)` (`ImageLocation.java:130-145`) sets `photoSize` only for stripped and path sizes. So deviation 9's "cached photo shows" never fires, and downloaded photos show the blur.
   - Taps on media with `buttonState == -1` (already on disk) never reach `didPressButton`, so A6b's `noteTapped` never runs. A photo or video opens the viewer (`ChatMessageCell.java:6031`, `:6064`). A GIF tap is swallowed outright: `:4342-4344` drops the press when `TYPE_GIF && buttonState == -1 && autoplay && photoImage.getAnimation() == null`, and G guarantees no animation.
   - Scenario: every photo and GIF you downloaded in a group before installing the build, and every GIF cached from another chat, is blurred permanently, and tapping a GIF does nothing. Test plan 4.3 step 11 fails.
   - Fix: test `location.photo != null && location.document == null` (or `location.location != null`). Call `TrustController.noteTapped` at the top of `didClickedImage()` too, the same rebind-and-return as in `didPressButton`.

## Low

7. **A voice tap chains into ungated downloads.** The first tap on a voice note plays as stock (deviation 7). `MediaController.checkIsNextVoiceFileDownloaded` (`MediaController.java:3099-3115`) then preloads the next voice in the playlist with `loadFile`, and the playlist auto-advances. Scenario: tap one stranger's voice note and the next ones download and play. Fix: gate `:3114`/`:3153` and the playlist build (`:1975`) on `allows(nextAudio)`.

8. **Premium sticker effects and single animated emoji autoplay through `EmojiAnimationsOverlay`.** `ChatActivity.java:16205-16207` calls `emojiAnimationsOverlay.onTapItem(cell, ..., false)` when the cell first appears. Its receivers' parent is the overlay, not the cell, so G does not apply. The effect file downloads and plays in untrusted chats. Official packs only, so low risk. Desktop finding 10 is the same class. Fix: skip the `onTapItem` call when `!allows(messageObject)`.

9. **A hand-marked bot decays like a person when the user isn't in the memory cache.** P457-466: `user == null` gives `KIND_PERSON`, so rule 3 (no decay) becomes rules 5-6. After 90 days, a trusted bot evaluated before its user loads (cold start, chat-list binding) is `WHY_DORMANT`, untrusted, and that verdict is cached for 60 s. Fix: when `user == null` and a mark exists, do not cache the verdict (or load the user from storage).

10. **The caller guard can't see Android's main bypass class.** `.github/media-callers.sh` android patterns: findings 3-8 are direct `FileLoader.loadFile(`, `getForVideoPath(`, `StoriesUtilities.setImage(` and overlay paths, none of which are counted. The engine's `p2p_allowed` (`VoIPService.java:3424`) is not counted either; only `udp_p2p` is. Fix: add `getForVideoPath(`, `p2p_allowed`, `new Instance.Config(`, and `loadFile(` restricted to `messenger/NotificationsController.java`, `messenger/MediaController.java`, `ui/Cells/` and `ui/Stories/`.

11. **Docs: the peer-set chat wallpaper is outside trust.md's "Not covered" list** (the log says so, the spec does not). Same as desktop finding 6.

## Checked, no defect found
- `TrustRules.decide`/`allowsMessage` vs §1: Never first (beats own messages and rule 8); Saved Messages and `777000` exact; rule 3 for non-persons with no decay; rule 4 = `chat.creator || broadcast && hasAdminRights` (no non-creator supergroup admin); rules 5→6→7 order; dormant label; rule 8 default off, Never-gated, persons in groups only, sender trusted by 5/6/7. `grace = 0` and window edges are correct. Defaults when prefs are missing: on, fails closed; values clamped.
- Desktop findings 1, 4, 7, 8, 9, 12, 13, 14: handled on Android as the log says (exact 777000, Never precedence, no toast in Never chats, dice/animated emoji exempt, viewers outside G's whitelist, unparseable marks kept, toast captures a dialog id).
- Gate G hot path: no DB or disk work; prefs read once; a few synchronized lookups and one array allocation only on refusal. The `setImageBackup`/attach replay runs the gate again (idempotent). `forceLoding` is reset at the top of the relayout block (`ChatMessageCell.java:7207`), before any `setImage`, so the belt cannot carry a tap over to a recycled cell. All `didPressButton` callers are touch or accessibility events, apart from `:18129` (needs `!autoPlayingMedia` after the GIF branch has set it: unreachable in practice).
- DownloadController: the 5 entries cover the forwarded-story bypasses and the background queue (`MessagesStorage.java:12817` uses `canDownloadMedia(message)`). RichMessageLayout receivers get the cell as parent view before loading (`setAllowLoadingOnAttachedOnly`), so G covers their thumbnails. `getForWebFile` null return: every caller handles null; inline-result cells use only proxied `TL_webDocument`.
- Calls: all four sites (`:1111`, `:1881`, `:3424`, `:4362`) use the account's `user` field; a null user fails closed (relay). Group calls have no P2P flag.
- Multi-account: every hook uses the right account (`messageObject.currentAccount` in G and taps, `currentAccount` elsewhere). Marks are keyed by user id; caches reset on a slot's user change.
- Activity SQL: correct table and primary key, `INSERT OR IGNORE`, prune, window `today-d+1..today`, day computed with the zone offset at the message's own date, and it runs on the storage queue. It stores only (uid, day).
- UI: the menu item is relabelled in `onShowSubMenu` after the lazy items are laid out; the toast checks that its fragment is still on top; the settings screen calls `saveSettings`, which clears every instance's cache.
- CI: the guard counts on stock `HEAD`; `TrustRulesTest` exits 1 on failure.
