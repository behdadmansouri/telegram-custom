# 8 accounts without Premium (2026-10-25)

Patches: `android/patches/0009-Eight-accounts-without-Premium.patch`, `desktop/patches/0008-Eight-accounts-without-Premium.patch`. Written against Android pin `9552e554` (12.10.3) and tdesktop 7.2.5 with the series 0001-0006 applied; both apply cleanly there (`git apply --check`, `git am`). Not compiled locally: CI is the compiler. Numbers 0007/0008 (Android) and 0007 (desktop) were left to parallel branches.

## Android: what is sized or switched by the account count

Grep of `MAX_ACCOUNT_COUNT`, `MAX_ACCOUNT_DEFAULT_COUNT`, `getMaxAccountCount` over `TMessagesProj/src/main/java` and `TMessagesProj/jni/tgnet` at the pin. There is no `FAKE_MAX_ACCOUNT_COUNT` at this pin.

| Place | What it does | Change |
|---|---|---|
| `UserConfig.java:27-28` | `MAX_ACCOUNT_DEFAULT_COUNT = 3`, `MAX_ACCOUNT_COUNT = 4` | both 8 |
| `UserConfig.java:124-126` `getMaxAccountCount()` | display only, returned 5 / 3 | returns the constant |
| `UserInfoActivity.java:474-492`, `MainTabsActivity.java:624-643`, `LogoutActivity.java:115-140` | add-account gate: non-Premium loses `MAX - DEFAULT` slots | none: the subtraction is now 0 |
| `UserInfoActivity.java:434-441` | footer "Subscribe to Premium to use up to N accounts" for non-Premium | shown only while `DEFAULT < MAX` (never now) |
| `NotificationsController.java:204` | summary notification id `account + 1` | slots 4-7 use `1000 + account`; 0-3 keep 1-4 (see below) |
| `jni/tgnet/Defines.h:30` | native `MAX_ACCOUNT_COUNT 5`: sizes `jniEnv[]` (`ConnectionsManager.cpp:40`) and the `setJava()` delegate loop (`TgNetWrapper.cpp:519`) | 8 |
| `jni/tgnet/ConnectionsManager.cpp:138-156` | `getInstance()` switch, cases 0-3, `case 4: default:` | cases 4-7, `default` on 7 |
| ~25 `new X[UserConfig.MAX_ACCOUNT_COUNT]` arrays, `for (a < MAX_ACCOUNT_COUNT)` loops, `isValidAccount()`, `NotificationsDisabledReceiver` bound, `StarsController [2][MAX]`, `DoubledLimitsBottomSheet:325` | follow the constant | none (the Premium comparison row now reads 8 / 8, cosmetic) |

Checked and clean: no bit-packed or multiplied account ids in Java (grep for `account <<`, `* account`, `account * N`); no Java caller passes an index >= `MAX_ACCOUNT_COUNT` to native; the App modules (`TMessagesProj_App*`) do not reference the constant. Per-account storage is string-keyed, so no ceiling: prefs `userconfing` (slot 0, legacy typo) / `userconfig1..`, dirs `files/account1..`, notification channels `account + "channel"`, group `"messages" + account`. Slots 0-3 keep their indices, so their data is untouched.

**Notification id collision (found here, not in the feasibility note).** Fixed service ids: 4 `VideoEncodingService`, 5 `MusicPlayerService` and `ImportingService`, 6 `LocationSharingService`, 33 story upload, 201/202 calls, 301 files migration. With `account + 1`, slots 4-7 would get 5-8: slot 4's summary would be replaced by the music player notification, slot 5's by live location. Slot 3 already shares id 4 with video encoding upstream (Premium users only); left as is to keep slots 0-3 identical.

**Native aliasing.** Without the native change, Java slots 5-7 would all resolve to native instance 4 (`default:`): several accounts on one connection and one `tgnet.dat`. Forks do the same native change: AyuGram4A 16 cases, Nekogram 8, Nagram 128 (feasibility note A1).

## Desktop

`main/main_domain.h:34-35` `kMaxAccounts` 3 -> 8, `kPremiumMaxAccounts` 6 -> 8. Every use checked (`grep` over `Telegram/SourceFiles`): `Domain::maxAccounts()` = `min(premium + 8, 8)` = 8; gates in `main_domain.cpp:329`, `settings_main.cpp:660`, `settings_information.cpp:1070,1203`; switch check `core/application.cpp:401,410`; assert `main_domain.cpp:272`; tdata bounds `storage_domain.cpp:164,178`; new account index is the lowest free one (`main_domain.cpp:295-297`), so it stays < 8. `premium_preview_box.cpp:1658-1669` and `premium_limits_box.cpp:1070-1071` show 8 / 8, cosmetic; the limit box is unreachable since the add button hides at 8. A tdata with more than 6 accounts will not load in stock Telegram Desktop; ours has its own data dir.

## Cost per slot

Not measured; the web search for fork reports failed (network error). What the source shows on Android: at app start `ApplicationLoader.java:248-273` creates `UserConfig`, `MessagesController`, `ConnectionsManager`, `ContactsController`, `DownloadController` for every slot, logged in or not, and each Java `ConnectionsManager` calls `native_init`, which starts one native network thread (`ConnectionsManager.cpp:3710`) plus an epoll fd (`:49`). So 4 extra empty slots = 4 more controller sets and 4 more idle network threads from boot. Desktop creates an `Account` only for logged-in accounts, so empty slots cost nothing there; each live account has its own MTProto session and caches.
