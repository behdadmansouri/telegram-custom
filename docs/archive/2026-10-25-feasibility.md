# Feasibility research, 2026-10-25

Read-only research for the patch series. Android source: DrKLO/Telegram at the pin 9552e554 (12.10.3). Paths are relative to `TMessagesProj/` unless noted. "Verified" means read in source at the pin; "inferred" means reasoning from the source. Line numbers are at the pin.

## A1. Android account limit

Verified in source:
- `src/main/java/org/telegram/messenger/UserConfig.java:27-28`: `MAX_ACCOUNT_DEFAULT_COUNT = 3` and `MAX_ACCOUNT_COUNT = 4`. The constant is the hard slot count (free = 3 usable, 4 with Premium). Both are `final static int`, so javac inlines them.
- `UserConfig.java:124-126`: `getMaxAccountCount() { return hasPremiumOnAccounts() ? 5 : 3; }`. This is display only (the "AddAccountInfo2" text and the Premium upsell shadow in `ui/UserInfoActivity.java:435-439`) and already disagrees with the constant (5 vs 4), so it is upstream sloppiness, not a gate.
- The real gate is the same 12-line block copied in three places: `ui/UserInfoActivity.java:474-492` (BUTTON_ADD_ACCOUNT click), `ui/MainTabsActivity.java:624-643` (account selector "Add account"), `ui/LogoutActivity.java:115-140` (the add-account row). Each counts unactivated slots into `freeAccounts`, then for non-Premium does `freeAccounts -= (UserConfig.MAX_ACCOUNT_COUNT - UserConfig.MAX_ACCOUNT_DEFAULT_COUNT);` and only opens `new LoginActivity(availableAccount)` if `freeAccounts > 0`; else shows `LimitReachedBottomSheet(TYPE_ACCOUNTS)`. The "Add account" row itself is hidden when `getActivatedAccountsCount() < MAX_ACCOUNT_COUNT` is false (`UserInfoActivity.java:422`, `MainTabsActivity.java:624`, `LogoutActivity.java:73`). `ui/Components/Premium/DoubledLimitsBottomSheet.java:325` shows the pair in the Premium comparison list.
- Because the gate is `MAX - DEFAULT` subtracted for non-Premium, setting `MAX_ACCOUNT_DEFAULT_COUNT = MAX_ACCOUNT_COUNT` makes the subtraction 0 and the free gate vanishes with no edits to the three call sites.

What the constant sizes (167 occurrences in 78 Java files, grep `MAX_ACCOUNT_COUNT`):
- Per-account singleton arrays: `UserConfig.java:87`, `ConnectionsManager.java:194`, `MessagesController.java:1502`, `MessagesStorage.java:113`, `NotificationCenter.java:418`, `FileLoader.java:231`, `DownloadController.java:243`, `NotificationsController.java:181`, `AccountInstance.java:11`, plus ~15 more (StarsController, BotStarsController, Business controllers, DialogsActivity.dialogsLoaded, SelectAnimatedEmojiDialog.preloaded, UserListPoller). All are `new X[UserConfig.MAX_ACCOUNT_COUNT]`, so they follow the constant automatically.
- Startup loops: `ApplicationLoader.java:248-262` and `:270-273` call `UserConfig.getInstance(a).loadConfig(); MessagesController.getInstance(a); ConnectionsManager.getInstance(a)` for EVERY slot at app start, activated or not. Raising to 16 instantiates 16 controller sets and 16 native ConnectionsManagers at boot (inferred cost: some tens of MB and a little startup time; not measured).
- Per-account state is keyed by string concatenation, so no ceiling: SharedPreferences `"userconfig" + currentAccount` (`UserConfig.java:415`), DB dir `"account" + currentAccount + "/"` (`MessagesStorage.java:312`), notification channel keys `currentAccount + "channel"` (`NotificationsController.java:412`). Note slot 0 uses the legacy `"userconfing"` name (`UserConfig.java:413`).
- NATIVE CODE is the real blocker. `jni/tgnet/ConnectionsManager.cpp:138-156` is a `switch (instanceNum)` with cases 0..3 and `case 4: default:` returning `instance4`. `jni/tgnet/Defines.h:30` has `#define MAX_ACCOUNT_COUNT 5` (sizes `jniEnv[]` at `ConnectionsManager.cpp:40`, loops at `TgNetWrapper.cpp:519`). Any Java slot index >= 5 would silently alias to native instance 4 (two accounts sharing one connection and `tgnet.dat`: corruption). So raising only the Java constant is unsafe past 5.
- Push: FCM registration is per account via the Java loop; irrelevant to our build because FCM does not work for our package id (see `android/customize.sh` comment). Contacts sync `checkAppAccount` (`ContactsController.java:398`) loops the constant, harmless.

Forks (fetched from raw GitHub, default branches, 2026-10-24):
- AyuGram4A (`rewrite` branch): `UserConfig.java:30-31` `MAX_ACCOUNT_DEFAULT_COUNT = 8; MAX_ACCOUNT_COUNT = 16`; `Defines.h:30` `#define MAX_ACCOUNT_COUNT 16`; `ConnectionsManager.cpp:138-186` switch extended to cases 0..15 (16 `static ConnectionsManager instanceN(N)` lines, `case 15: default:`).
- Nagram (NextAlone, `main`): `MAX_ACCOUNT_DEFAULT_COUNT = 8; MAX_ACCOUNT_PREMIUM_COUNT = 10; MAX_ACCOUNT_COUNT = 128`; `Defines.h` also 128.
- Nekogram (`main`): `MAX_ACCOUNT_DEFAULT_COUNT = 8; MAX_ACCOUNT_COUNT = 8`; `Defines.h` 8; switch extended.
- Cherrygram: repo not located at the guessed path (Cherrygram/Cherrygram 404), not checked.
So three of four forks raise it, to 8, 16 and 128, and all change both Java and native.

Server-side limit: not found in source (the client enforces everything; each login is just an `auth.signIn` session on its own auth key). The web search tool failed twice, so no documented per-device server cap was confirmed. Telegram does cap active sessions per account (~100, inferred from general knowledge, unverified here). The 3/4 cap is client policy used as a Premium upsell.

Patch: raise to 8 (what Nekogram does) or 16 (AyuGram). Java: `MAX_ACCOUNT_COUNT = 16`, `MAX_ACCOUNT_DEFAULT_COUNT = 16`, `getMaxAccountCount()` returns the constant. Native: `Defines.h` `MAX_ACCOUNT_COUNT 16` and extend the `switch` in `ConnectionsManager.cpp` with cases 5..15 (3 lines each). Shape: ~45 lines, 4 files, and the native build must be rebuilt (CI already does). The three Premium-upsell strings stay but are never reached. Patch size: small to medium (about 45 changed lines, mostly the repetitive switch).

## A2. Android: per-photo captions and ungrouped sending

Verified in source (paths under `src/main/java/org/telegram/`):
- Each selected photo has its own caption field today. `messenger/MediaController.java` `PhotoEntry` carries `caption` and `entities`. In the full-screen viewer, `ui/PhotoViewer.java:9895-9914` (`applyCaption()`) writes the text of the caption box into the CURRENT photo only: `photoEntry.caption = result[0]; photoEntry.entities = entities;`. Swipe to the next photo and type again, and it gets its own caption. Reopening shows it back via `updateCaptionTextForCurrentPhoto` (`PhotoViewer.java:11079`).
- A "same caption on all" mode exists and is the trap: `PhotoViewer.setCaption` (`PhotoViewer.java:1267-1271`) sets `hasCaptionForAllMedia = true` and shows ONE caption on every photo. It is turned on when the viewer opens from the grid while the chat attach bar's text field has text (`ChatAttachAlertPhotoLayout.java:1063-1064`, `if (captionForAllMedia()) PhotoViewer.getInstance().setCaption(...)`). It is turned off again only if you edit a caption on a photo that is not first in the selection order (`PhotoViewer.java:9904-9906`).
- The attach sheet's own text field is a first-photo-only caption: `ChatAttachAlertPhotoLayout.applyCaption(CharSequence)` (`:3566-3588`) loops the selection but only acts at `a == 0`. `ChatAttachAlert.applyCaption` (`:4439`) returns early when the field is empty, so an empty field never overwrites per-photo captions.
- Send paths: the viewer's own send button (`ChatAttachAlertPhotoLayout.java:523-575`, `sendButtonPressed`) has a gotcha: if `hasCaptionForAllMedia` is true it keeps the caption on photo 0 and nulls the rest (`:537-557`, `photoEntry1.caption = null`). Otherwise per-photo captions are kept.
- A "group / ungroup" option already exists: `ChatAttachAlertPhotoLayout.java:233` `group = 0`, `:786` `addSubItem(group, R.drawable.msg_ungroup, ...SendWithoutGrouping)`, string `res/values/strings.xml:3394` "Send without grouping". It sits in the 3-dot menu of the attach sheet and is shown only when 2+ items are selected, no Stars price, not editing (`:3465-3486`). Its handler (`:3245-3255`) calls `delegate.didPressedButton(7, false, ...)`. In `ui/ChatActivity.java:12574` the second parameter `arg` is passed straight into `SendMessagesHelper.prepareSendingMedia(..., forceDocument, arg /*groupMedia*/, ...)` (`:12645`, `:12647`). All normal send buttons pass `true` (`ChatAttachAlert.java:4465,4470`, `ChatAttachAlertPhotoLayout.java:570`).
- In `messenger/SendMessagesHelper.java:10659` (`prepareSendingMedia`) `groupMedia` only decides whether a `groupId` is added (`:10993-10999` photos, `:11250-11256` videos, `:11473-11480` the other photo path). Every item is built with its own `info.caption` and `info.entities` regardless (`SendMessageParams.of(..., info.caption, info.entities, ...)` at `:11005`, `:11275`, `:11489`). And `ChatActivity.java:12623` fills `info.caption = photoEntry.caption` per photo. So ungrouped = separate messages, each with its own caption. Verified.
- If grouped as an album: all captions are still sent per message, but the album bubble only shows one. `messenger/MessageObject.java:1383-1389` in `GroupedMessages.calculate`: first captioned message becomes `captionMessage`; a second captioned message sets `captionMessage = null` (for non-document albums). So with 2+ captions the album shows no caption at the bubble level (inferred: each caption is then only reachable by opening that photo in the viewer; I did not test on a device). Server limit of 10 per album is handled by `ChatActivity.java:12590` (`albumsCount = ceil(n/10)`).
- Any item with a self-destruct ttl forces ungrouped (`SendMessagesHelper.java:10663-10667`).

What the user sees today: select N photos, tap a photo, caption photo 1, swipe, caption photo 2 and so on, then either the check button (sent as one album, captions invisible or only one shown) or 3-dot menu then "Send without grouping" (N messages, each with its caption). Everything wanted already exists; the pain is that "Send without grouping" is the buried path and the main button groups.

Patch options, smallest first:
1. Default to ungrouped. In `ChatActivity.java:12645` and `:12647` replace the `arg` argument with `arg && !CustomSettings.sendUngrouped` (add a toggle to our existing `CustomSettings.java` that patches 0003-0005 already use). 2 lines in ChatActivity plus ~10 lines for the setting. Caveats: the viewer's send path with `hasCaptionForAllMedia` still nulls captions of photos 2..N (`ChatAttachAlertPhotoLayout.java:537-557`), so a user who types the attach-bar caption first still gets a caption only on photo 1; that is arguably correct behaviour.
2. Hard flip, no setting: change `true` to `false` at `ChatAttachAlert.java:4465`, `:4470` and `ChatAttachAlertPhotoLayout.java:570`. 3 one-word edits, but it ungroups sends of a single photo plus the bar caption too (harmless since one item is never grouped anyway) and loses the album option entirely unless the 3-dot "Send without grouping" is relabelled (its call would still pass `false`).
3. Make the grid's check-mark flow friendlier (open the viewer on tap per photo): no change needed, already how it works.
Patch size: option 1 about 15 lines across 2 files; option 2 3 lines. Merge risk: `ChatActivity.java` is a huge file but the two lines are stable; patch 0006 touches `ChatAttachAlert.java` near line 4001 (not near 4465), so no hunk collision seen.

## A3. Android in-app updates

Headline: our build is NOT the standalone module. The workflow runs `./gradlew :TMessagesProj_App:assembleAfatRelease` (`.github/workflows/android.yml:80`) and `android/customize.sh` edits `TMessagesProj_App/build.gradle` and `TMessagesProj_App/google-services.json`. `afat` is only an ABI flavor of the Play-style module `TMessagesProj_App` (namespace `org.telegram.messenger.regular`, `TMessagesProj_App/build.gradle` near the end). The real standalone (direct-APK) code lives in a different module, `TMessagesProj_AppStandalone` (its `ApplicationLoaderImpl` overrides `isStandalone() { return true; }`, line 12 of its `ApplicationLoaderImpl.java`), and is not compiled into our APK. The `standalone` build type with `applicationIdSuffix ".web"` (`TMessagesProj_App/build.gradle:79-87`) is also not what we build (`release`).

Verified in source (paths under `TMessagesProj/src/main/java/org/telegram/` unless noted):
- Our `TMessagesProj_App/src/main/java/org/telegram/messenger/ApplicationLoaderImpl.java` overrides only `onGetApplicationId()`. So `ApplicationLoader.isStandalone()` and `isBeta()` return the base-class `false` (`messenger/ApplicationLoader.java:147-153`), `isCustomUpdate()` is `false` (`:697`), `takeUpdateLayout()` returns `null` (`:653`), `showUpdateAppPopup()` returns `false` (`:645`), `openApkInstall()` returns `false` (`:640`).
- `ui/LaunchActivity.java:5957-5960`: `checkAppUpdate(boolean force, ...)` begins `if (!ApplicationLoader.isStandaloneBuild() && !ApplicationLoader.isBetaBuild()) { return; }`. So `help.getAppUpdate` (`TL_help_getAppUpdate`, built at `:5988`, with `req.source` = installer package name) is never sent, from the startup call (`:7032`) or the debug-menu "Check app update" (`SettingsActivity.java:1540`, `ProfileActivity.java:4787`, both also gated at `:1431`/`:4682`).
- `SharedConfig.isAppUpdateAvailable()` (`messenger/SharedConfig.java:777-790`) returns false unless `ApplicationLoader.isStandaloneBuild()`. `SharedConfig.pendingAppUpdate` (`:332`) can still be loaded from prefs (`:563`) or set by `FileRefController.java:1271,1630` (file-reference refresh), but that path only runs when something downloads the update document, and nothing initiates that. The blocking `can_not_skip` screen (`LaunchActivity.java:7029`) needs a non-null `pendingAppUpdate`, so it cannot trigger either (inferred: no code path sets it in our build).
- `UpdateAppAlertDialog` and `UpdateLayout` (the "Update Telegram" button) exist only in `TMessagesProj_AppStandalone/src/main/java/org/telegram/ui/Components/`, so they are not in our APK. There is no side drawer in 12.10 (bottom tabs, `MainTabsActivity.java:389` calls `takeUpdateLayout`, which returns null for us).
- If the server offered an update: nothing happens, no request, no dialog, no download of the official APK. Even if it did, the official APK has the stock package id and signing key and would not install over `org.telegram.messenger.custom`.
- `REQUEST_INSTALL_PACKAGES`: declared in `TMessagesProj/src/main/AndroidManifest.xml:62` (library manifest, so it merges into the app; inferred from manifest merging, not checked in a built APK). Install flow still needs the per-app "Install unknown apps" toggle (`messenger/AndroidUtilities.java:4293` checks `canRequestPackageInstalls()`).

Minimal patch to disable: none, already disabled. Do NOT override `isStandalone()` (that would switch on the server update path plus Stars/TON/billing standalone behaviours spread over ~25 call sites, grep `isStandaloneBuild`).

Minimal patch to redirect to GitHub Releases, three tiers:
1. No code: use Obtainium (see P2). Zero lines.
2. A tap-to-open entry: add one item to the Settings/profile screen that calls `Browser.openUrl(ctx, "https://github.com/<owner>/telegram-custom/releases/latest")`. About 8 lines, needs a `lint-ok:` on the URL line because `.github/patch-lint.sh` rejects added URLs. Note `releases/latest` resolves to the latest release with `latest=true`, which `.github/release.sh` sets only for android (desktop is `latest=false`), so the redirect lands on the Android release.
3. Real in-app updater using the hooks the Beta module uses: override in `TMessagesProj_App/.../ApplicationLoaderImpl`: `isBeta()` true (needed to pass the `LaunchActivity.java:5958` gate), `isCustomUpdate()` true, `checkUpdate(force, whenDone)`, `getUpdate()` returning a `BetaUpdate` (`messenger/BetaUpdate.java`), `downloadUpdate()`, `isDownloadingUpdate()`, `getDownloadedUpdateFile()`, `showCustomUpdateAppPopup()`, and `takeUpdateLayout()` (an `IUpdateLayout`). The reference implementation is `TMessagesProj_AppHockeyApp/src/main/java/org/telegram/messenger/ApplicationLoaderImpl.java` lines 196-263. Setting `isBeta()` true has side effects elsewhere (`BuildVars.isBetaApp()`, MessageObject/MessagesController `isBetaApp` branches). Size: roughly 250-400 lines (GitHub API call + JSON + download + a dialog + PackageInstaller or ACTION_VIEW), plus it breaks the README promise (no network code) so `patch-lint.sh` would need exceptions on many lines. Not recommended; Obtainium does this better.

Patch size: disable = 0 lines; redirect tier 2 = ~8 lines, tier 3 = ~300 lines.

## A4. Android version string

Verified in source:
- Two places format it, both from `PackageInfo`: `ui/SettingsActivity.java:917-936` `getVersionName()` returns `formatString(R.string.TelegramVersion, String.format(Locale.US, "v%s (%d)\n%s", pInfo.versionName, code, abi))` where `code = versionCode / 10` and `abi` is `"universal " + Build.CPU_ABI + ...` for us (the `%10 == 9` branch, non-standalone). Result like "Telegram for Android v12.10.3 (7089)\nuniversal arm64-v8a ...". String is `res/values/strings.xml:2630` `Telegram for Android %1$s`; 8 locale files override `TelegramVersion`, so editing the string with sed would miss those languages.
- `messenger/AndroidUtilities.java:6642-6661` `getBuildVersionInfo()`, same format on one line. Used for the version footer row in Settings (`ui/ProfileActivity.java:13308-13314`, `versionRow` added at `:10688`; long-press opens the debug menu at `:4666`) and in crash/parse-error dialogs (`LaunchActivity.java:7686,7692,7723`). In 12.10 this ProfileActivity footer is the visible Settings version line (inferred: `SettingsActivity` is still reachable via `LaunchActivity.java:613,3135` and `LinkManager`; patch both).
- No version string in a side drawer: there is no drawer in this version (no `DrawerLayoutAdapter`/`DrawerProfileCell` in the tree).
- versionName is `APP_VERSION_NAME=12.10.3` and versionCode `APP_VERSION_CODE=7089` (`gradle.properties:16-17`), final code = `7089 * 10 + 9` (`TMessagesProj_App/build.gradle` `versionCodeOverride`).
- Do NOT put the build number into `versionName`: it is sent to the Telegram servers as `appVersion = pInfo.versionName + " (" + pInfo.versionCode + ")"` (`tgnet/ConnectionsManager.java:228`, shown in other devices' session lists), copied into login/support emails (`LoginActivity.java:1256` etc.) and into the bot-WebView user agent (`ui/web/BotWebViewContainer.java:497`). `SharedConfig.versionBiggerOrEqual` (`messenger/SharedConfig.java:818-831`) does `Integer.parseInt` on dot-separated parts, so a suffix like `-b42` would throw if that function ever runs (only in update flows our build has off).

Minimal patch: UI-only, two format calls. Add a constant (for example in the `CustomSettings.java` that patches 0003-0005 already create, `public static final String BUILD_LABEL = "b0"`), have `android/customize.sh` rewrite it with `sed -i "s/BUILD_LABEL = \"b0\"/BUILD_LABEL = \"b$GITHUB_RUN_NUMBER\"/"` (same style as its existing `APP_ID` sed), and append it in `SettingsActivity.java:936` (after the `%s (%d)`) and `AndroidUtilities.java:6661`. A BuildConfig field is not an option for the app module: the library's `org.telegram.messenger.BuildConfig` is generated in `TMessagesProj/build.gradle:164-210` per build type, so a `buildConfigField` there needs a sed into that file instead of one constant; the constant is simpler. `GITHUB_RUN_NUMBER` matches the release tag `android-v<ver>-b<run>` that `.github/release.sh:14` already builds, so the on-screen label equals the tag suffix.
Patch size: about 5 lines of Java in 2-3 files plus 1 sed line in `customize.sh`. Lint: clean (no URL, network or permission).

## A5. Android hardening defaults

All verified in source at the pin (`src/main/java/org/telegram/`). Important caveat for every "default" below: stored prefs win over code defaults, and the server can overwrite some presets, so a code-default flip only affects a fresh install (or after "clear data"). Where a hard override is cheap, it is named.

Auto-download (`messenger/DownloadController.java`):
- Defaults are three strings at `:262-264`, format `mask0_mask1_mask2_mask3_photoMax_videoMax_docMax_audioMax_preloadVideo_preloadMusic_enabled_lessCallData_maxVideoBitrate_preloadStories`:
  - `defaultLow    = "1_1_1_1_1048576_512000_512000_524288_0_0_1_1_50_0"`
  - `defaultMedium = "13_13_13_13_1048576_10485760_1048576_524288_1_1_1_0_100_1"`
  - `defaultHigh   = "13_13_13_13_1048576_15728640_3145728_524288_1_1_1_0_100_1"`
  Mask bits (`:48-51`): photo 1, audio 2, video 4, document 8. So medium/high = photos + videos + files (13), in all four chat classes (contact, private, group, channel); low = photos only (1).
- Network mapping (`:270-272`): `mobilePreset` = defaultMedium, `wifiPreset` = defaultHigh, `roamingPreset` = defaultLow. Preset index defaults `currentMobilePreset/WifiPreset/RoamingPreset = 3` (custom) at `:273-275`. Limits: mobile 1 MB photo, 10 MB video, 1 MB file; Wi-Fi 1 MB photo, 15 MB video, 3 MB file; roaming photos only, 500 KB video/file; music preload 512 KB.
- The master switch per network is `Preset.enabled` (field 11 of the string, `_1_` after `preloadMusic`). `getCurrentDownloadMask()` (`:1035-1063`) returns 0 when `!wifiPreset.enabled` / `!roamingPreset.enabled` / `!mobilePreset.enabled`, and `canPreloadStories()` (`:1788-1815`) returns false under the same condition. So `enabled=false` on the three presets kills media auto-download AND stories preloading at one gate.
- Server overwrite: `account.getAutoDownloadSettings` response replaces low/medium/high and any network preset equal to them (`:355-385`), and `Preset.set(TL_autoDownloadSettings)` (`:138-170`) rewrites the masks and force-sets `preloadStories = true` (`// TODO stories`, "fill flag from server"). It does NOT touch `enabled`. That makes `enabled` the robust knob; changing the size or mask defaults is not.
- Patch to flip: change `_1_` to `_0_` in the enabled field of the three default strings (3 edits in `:262-264`) for fresh installs; plus for existing prefs, after the constructor assigns the presets (end of `DownloadController(int)` near `:318`), force `mobilePreset.enabled = wifiPreset.enabled = roamingPreset.enabled = false;`. Roughly 4 lines. The user can still tap to download any item manually. Alternative middle ground (photos on Wi-Fi only): set masks, not worth it.
- Stories specifically ("load media automatically in stories"): there is no separate toggle, only `Preset.preloadStories` (field 14; medium/high default `_1`, low `_0`; `DataAutoDownloadActivity.java:268`, `:724`). Gated by `enabled` as above.

Autoplay GIFs and videos (`messenger/LiteMode.java`):
- Flags `FLAG_AUTOPLAY_VIDEOS = 1024` and `FLAG_AUTOPLAY_GIFS = 2048` (`:46-47`). Presets: `PRESET_LOW` has GIFs only (`:52-59`), `PRESET_MEDIUM` and `PRESET_HIGH` have both (`:60-85`). The default preset is chosen by device performance class (`loadPreference()`, `:201-210`) and persisted under `lite_mode6` (`:280`). The server can replace the three presets (`updatePresets`, `:176-184`, "settings_mask").
- Robust single choke point: `LiteMode.isEnabled(int flag)` (`:149-155`). Adding `if ((flag & (FLAG_AUTOPLAY_VIDEOS | FLAG_AUTOPLAY_GIFS)) != 0) return false;` at its top overrides prefs and server presets. 1-2 lines. Side effect: the Settings > Power Saving toggles for them turn cosmetic. Softer option: mask the two bits out of `defaultValue` before `:280` (fresh installs only).

Link previews:
- Receiving: the preview card is server-built and arrives in the message as `MessageMedia.webpage`; the client only downloads its photo from Telegram's servers. There is no client setting to hide it on Android (verified: no such pref in `SharedConfig`/`MessagesController`). Hiding it would be a render-time patch (not scoped here, inferred as 5-15 lines in `ChatMessageCell`).
- While typing in normal chats: `ChatActivity.searchLinks(...)` (`ui/ChatActivity.java:14086`) sends `TL_account.getWebPagePreview` (`:14221`), i.e. the TYPED URL goes to Telegram's server to be fetched (privacy cost is toward Telegram, not toward the linked site's logs). Disable: add an early `return;` at the top of `searchLinks`, 1 line (no preview card while composing; sent links still get a server-side preview unless `no_webpage` is set on send, a separate path not checked).
- Secret chats: `MessagesController.secretWebpagePreview` default `2` ("ask") at `messenger/MessagesController.java:1579` (`getInt("secretWebpage2", 2)`); `ChatActivity.java:14201-14216` shows the consent dialog when it is 2 and sets it to 0 meanwhile; a toggle exists in `ui/PrivacySettingsActivity.java:499-507`. `searchLinks` returns early for secret chats when it is 0 (`ChatActivity.java:14086`). Flip: change the default `2` to `0` (1 token). A fresh install then never prompts and never previews; the privacy toggle turns it on.

P2P in calls:
- Client side: all three call protocols advertise P2P: `messenger/voip/VoIPService.java:1108` (`reqCall.protocol.udp_p2p = true`, outgoing), `:1877` and `:4367` (`udp_p2p = udp_reflector = true`, accepting). The actual engine flag is `privateCall.p2p_allowed` passed into `Instance.Config` at `:3420`.
- Server side: who may P2P you is the account-wide "Peer-to-peer" privacy rule (`ContactsController.PRIVACY_RULES_TYPE_P2P`, `ContactsController.java:95`, UI in `PrivacySettingsActivity.java:868,926`). That is stored on Telegram's servers, so setting it to "Nobody" is a per-account action, not a patch.
- Patch: replace `privateCall.p2p_allowed` with `false` at `:3420` (1 token) and optionally `udp_p2p = false` at the three request sites. Effect: calls relay through Telegram, hiding your IP from the peer. Tradeoff: slightly higher latency. Inferred: the other side's client may still offer P2P, but our engine will not use it.

## D1. Desktop account limit

Source: tdesktop v7.2.5 (paths under `Telegram/SourceFiles/`). Verified:

## P1. Android silent self-update (PackageInstaller USER_ACTION_NOT_REQUIRED)

Evidence note: developer.android.com returned HTTP 403 to the search tool, so the text below is the AOSP Javadoc that the site is generated from, read from the AOSP mirror: `github.com/aosp-mirror/platform_frameworks_base`, `core/java/android/content/pm/PackageInstaller.java`, `SessionParams.setRequireUserAction(int)` (lines 3464-3520 on `master`, 2026-10-24) and `core/res/AndroidManifest.xml:8234-8238`. This is the same documentation as the "PackageInstaller.SessionParams" reference page (`developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)`).

Exact conditions (verified in that Javadoc). The installer must hold `REQUEST_INSTALL_PACKAGES` and ALL of these must hold:
1. `SessionParams.setRequireUserAction(USER_ACTION_NOT_REQUIRED)` is set (unspecified behaves as REQUIRED for installers that hold `REQUEST_INSTALL_PACKAGES`).
2. The app being installed has `targetSdkVersion` at least: API 29 on Android 12 (S, API 31); API 30 on Android 13 (T, API 33); API 31 on Android 14 (U, API 34); API 33 on Android 15 (V, API 35). The doc adds: "The target API level requirement will advance in future Android versions." Our APK targets 36 (`TMessagesProj_App/build.gradle` `targetSdkVersion 36`), so this passes on all four.
3. The installer is one of: (a) the update owner of the existing app when update-ownership enforcement is on (Android 14+, set by the installer with `setRequestUpdateOwnership`), (b) the installer of record (`InstallSourceInfo.getInstallingPackageName()`) of the existing app when enforcement is off, or (c) "Updating itself".
4. The installer declares `android.permission.UPDATE_PACKAGES_WITHOUT_USER_ACTION` (added in API 31; protection level `normal`, so no runtime grant, only a manifest line).
The Javadoc also says to always be prepared for `STATUS_PENDING_USER_ACTION`: the system may still ask.

Applied to us:
- App updating itself: clause 3(c) means a Telegram Custom build that holds `REQUEST_INSTALL_PACKAGES` (it does, see A3) plus `UPDATE_PACKAGES_WITHOUT_USER_ACTION` could update itself with no tap on Android 12-15, regardless of how it was first installed. Needs the user to have enabled "Install unknown apps" for it once (`canRequestPackageInstalls()`, `AndroidUtilities.java:4293`). It would need two manifest/code additions (the permission line and a PackageInstaller session in code), which `patch-lint.sh` flags (permission, network download); inferred size 150-300 lines.
- A third-party installer (Obtainium, Droid-ify) qualifies only via 3(a) or 3(b), i.e. it must be the installer of record of the already-installed build. A sideloaded APK installed from a browser or file manager makes THAT app (or the system installer, `com.google.android.packageinstaller`) the installer of record, so the first update through Obtainium needs a tap; after that update, Obtainium is the installer of record and later updates can be silent. Inferred from the clause wording; the Obtainium wiki states the same practical rule (see P2).
- Android 11 and below: none of this exists (needs API 31); user action always required (inferred from "on Android S" being the first listed level).
Patch size: not needed if Obtainium is used. Self-updater: 150-300 lines plus lint exceptions.

## P2. Obtainium

Sources: Obtainium wiki pages `wiki.obtainium.imranr.dev/app_tracking/`, `/sources/`, `/ui_overview/`, and source `github.com/ImranR98/Obtainium` (`lib/app_sources/github.dart`, `lib/providers/apps_provider.dart`, read 2026-10-24).
- Track one repo's GitHub Releases: yes. Source "GitHub" accepts the repo URL, options in `github.dart`: include prereleases, "Filter release titles by regular expression" (`filterReleaseTitlesByRegEx`, `github.dart:116`, with an invert switch), "Filter release notes by regex" (`:135`), "Verify latest tag" (`:152`), "Release title as version" (`:179`), and an APK filter by regex (`apkFilterRegEx`, `:713`, with invert) plus sort method. There is no tag-prefix filter. The title filter is applied to the release `name`, falling back to `tag_name` only when the name is empty (`github.dart:659-664`). In this repo `.github/release.sh` titles releases "Android <ver>" and "Desktop <ver> (Manjaro/Arch)" and tags them `android-v<ver>-b<run>` / `desktop-v...`, so the working filters are: title regex `^Android` (or invert on `^Desktop`), APK regex `\.apk$`. A tag-style filter `android-v.*` would NOT work as written (inferred from the code path above).
- Background checks: yes. Wiki "Background Updates": checks on an interval set in Settings via WorkManager (default) or an optional foreground service (Android 11+), optional Wi-Fi-only and charging-only constraints, plus "check on start".
- Update without a tap, wiki "Silent Installation" criteria, verbatim list: OS Android 12 or higher; the app targets a recent API level (the link goes to the `setRequireUserAction` doc, matches P1); "The currently installed version of the app must have been installed by Obtainium"; background updates enabled globally and per app; and the update must resolve to one APK. Shizuku is NOT required for this; it is an optional setting for "elevated silent installs" (wiki UI overview, Settings > Updates, also "pretend to be Google Play"), relevant on older Android or when the installer-of-record rule is not met. The wiki warns a failed silent install gives no error notification.
- Version comparison gotcha (relevant to our tags): Obtainium compares the Android-reported versionName with the source version in "standard formats" and disables version detection if they differ in format (wiki "Version Detection"). Our versionName stays `12.10.3` across rebuilds of one upstream (`gradle.properties:17`) while the tag is `android-v12.10.3-b42`, so detection is probably off and Obtainium would rely on its own record of what it last installed. Options: set "Release title as version" or accept the stored-state behaviour. Both builds of the same upstream have the same versionCode too (`7089*10+9`); Android lets a session reinstall an equal versionCode with the same key (inferred, not tested), so a rebuilt APK of an unchanged upstream would still install.
- Also useful: Obtainium has a Telegram source (unrelated to us) and "Verified Apps"/AppVerifier integration that checks the APK signing cert hash; our release body already prints SHA-256 and `actions/attest` runs on `main` (`android.yml:101`).
Patch size: none. Setup is a one-time config: add URL of the repo, title regex `^Android`, APK regex `\.apk$`, install the first build through Obtainium so it becomes the installer of record.
